# 04. .cursorrules 다단계 보고서 - Prompting 기록

## 1. 목적

이 문서는 이번 세션에서 `.cursorrules`를 YAML 구조로 재정리하고 실제 파일에 반영하기 위해 사용한 사용자 프롬프트와 산출 과정을 기록한다.

이번 세션은 구현 코드 변경이 아니라 Cursor AI 규칙 파일을 단계적으로 설계하고 반영하는 데 초점을 맞췄다.

## 3. 산출 과정 요약

### 3.1. YAML 뼈대 산출

첫 번째 산출에서는 `.cursorrules`의 최상위 YAML 키만 구성했다.

사용한 최상위 키는 다음과 같다.

- `project`
- `code_style`
- `architecture`
- `tdd_rules`
- `testing`
- `forbidden`
- `file_structure`
- `ai_behavior`

각 최상위 키 앞에는 80자 폭의 `#` 구분선 주석을 추가했다.

### 3.2. TDD 단계 구조 산출

두 번째 산출에서는 `tdd_rules` 하위 구조를 정의했다.

`Java UnitConverter`를 기준으로 `red_phase`, `green_phase`, `refactor_phase`를 두고, 각 단계에 `description`, `rules`, `must_not`를 포함하도록 했다.

초기 응답은 구조 중심이었고, 이후 전체 YAML 작성 단계에서 실제 규칙 문장을 완성했다.

### 3.3. 기존 파일 검토

기존 `.cursorrules`는 자연어 규칙 문서 형태였다.

검토 결과는 다음과 같았다.

- YAML 문법 기준으로 안전한 구조가 아니었다.
- 요청된 최상위 YAML 섹션이 누락되어 있었다.
- `tdd_rules`와 `forbidden` 섹션이 없어서 충돌 여부는 판단할 수 없었다.
- 테스트 green 보장과 backward compatibility 보장 같은 일부 규칙은 Cursor가 항상 지키기 어려운 규칙으로 분류했다.

### 3.4. 전체 YAML 완성

전체 YAML 작성 단계에서는 다음 요구사항을 반영했다.

- Java 21
- Google Java Format
- Java 네이밍 규칙
- `boundary`, `control`, `entity` 패키지 및 모듈 분리
- BCE 계층 정의
- 의존성 방향
- JUnit 5 고정
- AAA 테스트 구조
- fixture 규칙
- 커버리지 기준
- 금지 패턴별 `pattern`, `reason`, `alternative`
- 파일 구조 트리 주석
- AI 행동 규칙

### 3.5. 실제 파일 반영

최종 단계에서는 기존 `.cursorrules` 파일을 전체 YAML 구조로 교체했다.

이때 기존 파일에 있던 feedback data의 `text` 컬럼 도메인 규칙은 `project.domain_rules`에 보존했다.

반영 후 `.cursorrules`에 대해 linter 진단을 확인했고, 오류는 없었다.

## 4. 최종 .cursorrules 핵심 구조

최종 `.cursorrules`는 다음 섹션으로 구성되었다.

```yaml
project:
code_style:
architecture:
tdd_rules:
testing:
forbidden:
file_structure:
ai_behavior:
```

## 5. 주요 규칙 요약

최종 규칙의 핵심은 다음과 같다.

- Java 21과 Google Java Format을 기준으로 한다.
- `boundary -> control -> entity` 의존성 방향을 지킨다.
- `entity`는 외부 입출력, Spring MVC, Thymeleaf, 파일 시스템 세부사항에 의존하지 않는다.
- 새 기능이나 버그 수정은 가능한 한 테스트를 먼저 작성한다.
- 리팩터링은 관련 테스트가 green인 상태에서만 수행한다.
- JUnit 5와 AAA 구조를 사용한다.
- 반복 fixture는 의도가 드러나는 메서드나 상수로 분리한다.
- `System.out` 디버그 남발, 매직 넘버, 무시하는 `catch(Exception)`, public 필드 남용, God class를 금지한다.

## 6. 검증

파일 반영 후 진단 결과는 다음과 같았다.

```text
No linter errors found.
```

이번 세션에서는 Java 프로덕션 코드나 테스트 코드를 변경하지 않았으므로 Maven 테스트는 실행하지 않았다.
