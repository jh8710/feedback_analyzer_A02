## 3. 참고한 프로젝트 맥락

분석 과정에서는 프로젝트의 기존 문서와 규칙을 참고했다.

주요 확인 내용은 다음과 같다.

- 고객 피드백 분석 시스템은 수동 입력과 CSV 업로드를 통해 피드백을 수집한다.
- 감정 분석, 키워드 기반 카테고리 분류, 필터링, 결과 다운로드 기능을 제공한다.
- 초기 버전은 리팩토링 학습을 위해 의도적으로 코드 스멜과 안티패턴을 포함한다.
- 필수 입력 데이터에는 실제 피드백 내용을 담는 텍스트 컬럼이 필요하다.
- 현재 구조는 책임 분리, 입력 검증, 분석 기준 일관성, 상태 관리, 출력 포맷 측면에서 개선 여지가 크다.

## 4. 산출 내용 요약

### 4.1. 문제 정의 관점

문제는 단순히 고객 피드백 분석 기능이 부족하다는 것이 아니라, 입력에서 출력까지 분석 기준이 일관되게 관리되지 않는다는 점으로 정의했다.

핵심 관점은 다음과 같다.

- 사용자는 분석 결과의 이유와 기준을 이해해야 한다.
- 수동 입력과 CSV 입력은 서로 다른 진입점일 뿐, 같은 검증과 분석 흐름을 거쳐야 한다.
- 감정과 카테고리 기준은 분석, 필터, 화면, 다운로드에서 동일하게 사용되어야 한다.
- 변경 가능성이 높은 정책은 코드 내부 고정값이 아니라 외부화와 등록 가능한 단위로 다뤄야 한다.

### 4.2. Mom Test 관점

Mom Test 질문은 기능 선호를 묻지 않고 과거의 실제 경험을 묻도록 구성했다.

질문 설계 기준은 다음과 같다.

- 과거에 고객 피드백이나 리뷰를 실제로 분류한 경험이 있는가
- 어떤 자료를 받았고 어떤 순서로 정리했는가
- 기준 변경, 입력 오류, 결과 불일치가 실제로 시간과 비용을 발생시켰는가
- 리팩토링 학습자가 구조 문제를 실제 문제로 인식하는가
- 단순 출력 결과라도 설명 가능성과 추적 가능성을 필요로 하는가

### 4.3. 위험 가정 관점

진짜 위험 가정은 다음 세 가지로 정리했다.

- 학습자와 사용자가 기준 불일치를 실제 고통으로 느끼는가
- 단순 입력과 조건 분기 기반 변환 구조가 현실적인 학습 문제를 충분히 드러내는가
- 단순한 출력 결과에도 설명 가능성과 추적 가능성에 대한 필요가 있는가
