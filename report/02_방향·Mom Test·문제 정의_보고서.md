# 02. 방향·Mom Test·문제 정의 보고서

## 1. 세션 목적

이번 세션의 목적은 고객 피드백 분석 시스템을 제품 기능 관점이 아니라 학습자와 사용자의 실제 행동 관점에서 다시 바라보고, 리팩토링의 출발점이 되는 문제 정의를 정리하는 것이다.

특히 현재 구조를 단순한 기능 부족으로 해석하지 않고, 입력, 변환, 분석 기준, 필터링, 출력 결과가 서로 어떻게 연결되어야 하는지에 초점을 맞췄다.

주요 수행 내용은 다음과 같다.

- 고객 피드백 분석 시스템 사용자가 겪는 어려움 관찰
- 기존 소스 구조의 잠재적 문제 정리
- OCP, SRP, 입력 검증, 설정 외부화, 동적 단위 등록, 출력 포맷 관점 연결
- 고객 인터뷰를 위한 Mom Test 질문 작성
- 최종 문제 정의와 핵심 Invariant 도출

## 2. Observation

### 2.1. 사용자가 겪는 어려움

고객 피드백 분석 시스템 사용자는 피드백을 입력한 뒤 결과를 확인할 수는 있지만, 결과가 어떤 기준으로 산출되었는지 확신하기 어렵다.

특히 감정, 카테고리, 필터링, 다운로드 결과가 같은 기준을 공유하지 않으면 사용자는 분석 결과를 신뢰하기 어렵다. 입력 형식이 틀렸거나 CSV 컬럼이 잘못된 경우에도 명확한 검증 피드백이 없다면 데이터 문제와 시스템 문제를 구분하기 힘들다.

즉 사용자의 어려움은 단순히 “분석 기능이 부족하다”가 아니라 “분석 결과를 믿고 설명할 수 있는 구조가 부족하다”에 가깝다.

### 2.2. 기존 소스 구조의 문제

현재 구조는 사용자 요청 처리, 입력 검증, 상태 관리, 분석, 필터링, CSV 입출력, 화면 출력의 책임이 명확히 분리되어 있지 않다.

이 구조에서는 작은 정책 변경도 여러 책임 영역에 동시에 영향을 준다. 예를 들어 감정 키워드나 카테고리 기준이 바뀌면 분석 결과, 필터 결과, 화면 선택지, 다운로드 결과까지 함께 흔들릴 수 있다.

분석 기준과 필터 기준이 중복 관리되면 같은 문장이 통계에서는 특정 감정으로 집계되지만 필터링에서는 다른 기준으로 처리되는 문제가 발생할 수 있다.

### 2.3. 품질 관점 연결

- SRP 관점에서는 요청 처리, 검증, 분석, 저장, 출력의 변경 이유가 분리되어야 한다.
- OCP 관점에서는 감정, 카테고리, 출력 포맷 추가가 기존 흐름의 직접 수정으로 이어지지 않아야 한다.
- 입력 검증 관점에서는 수동 입력과 CSV 입력이 분석 전에 같은 필수 조건을 통과해야 한다.
- 설정 외부화 관점에서는 감정 키워드와 카테고리 정책이 코드 내부 고정값이 아니라 변경 가능한 규칙으로 관리되어야 한다.
- 동적 단위 등록 관점에서는 새로운 감정, 카테고리, 분석 단위가 등록만으로 전체 흐름에 반영되어야 한다.
- 출력 포맷 관점에서는 화면 표시와 다운로드 결과가 동일한 분석 결과 원천에서 생성되어야 한다.

## 3. 현재 구조로 발생할 수 있는 잠재 이슈

첫째, 사용자별 상태가 분리되지 않으면 한 사용자의 피드백이나 필터 결과가 다른 사용자에게 섞일 수 있다. 이는 분석 시스템에서 신뢰를 크게 훼손하는 문제다.

둘째, 분석 기준과 필터 기준이 별도로 존재하면 통계 결과와 목록 결과가 서로 맞지 않을 수 있다. 사용자는 같은 데이터를 보고도 서로 다른 결론을 얻게 된다.

셋째, CSV 입력 검증이 약하면 잘못된 파일이 일부 처리되거나 정상 파일이 실패할 수 있다. 이 경우 사용자는 데이터 오류인지 시스템 오류인지 판단하기 어렵다.

넷째, 출력 포맷이 명확히 관리되지 않으면 쉼표, 줄바꿈, 따옴표 같은 텍스트 특성 때문에 다운로드 결과가 깨질 수 있다.

다섯째, 분석 정책이 코드에 고정되면 새로운 카테고리나 감정 단위를 추가할 때 여러 곳을 수정해야 하며, 이는 누락과 회귀 오류를 만든다.

## 4. 개선 방향

개선 방향은 기능을 더 많이 넣는 것이 아니라 기준을 하나로 만들고 책임을 분리하는 것이다.

입력 방식은 수동 입력과 CSV 업로드로 나뉘더라도 내부에서는 같은 검증 규칙과 같은 분석 흐름을 거쳐야 한다. 그래야 사용자가 직접 입력한 결과와 파일로 입력한 결과가 일관된다.

감정과 카테고리 규칙은 하나의 정책 원천에서 관리되어야 한다. 분석 결과, 필터 조건, 화면 선택지, 다운로드 결과가 같은 정책을 바라보면 결과 불일치를 줄일 수 있다.

또한 새로운 감정 단위나 카테고리 단위를 추가할 때 기존 흐름을 직접 수정하지 않고 등록만으로 반영되는 방향이 적절하다. 이는 리팩토링 학습에서 OCP를 훈련하기 좋은 지점이다.

출력은 화면용 결과와 다운로드용 결과가 서로 다른 임시 데이터에 의존하지 않고, 동일한 분석 결과를 각 포맷에 맞게 표현해야 한다.

## 5. 입력 방식에 대한 해석

수동 입력은 가장 작은 단위의 피드백을 빠르게 확인하기 위한 방식이다. 사용자는 단일 문장을 넣고 감정과 카테고리 분류가 어떻게 되는지 즉시 확인할 수 있다.

CSV 입력은 실제 고객 피드백이 대량 데이터로 존재하는 경우를 다루기 위한 방식이다. 여러 건의 피드백을 한 번에 분석하고, 통계와 필터링 결과를 확인하기 위해 필요하다.

따라서 수동 입력은 개별 검증에 적합하고, CSV 입력은 대량 분석에 적합하다. 다만 두 입력 방식은 서로 다른 기능처럼 보이더라도 내부에서는 같은 검증 규칙과 분석 기준을 공유해야 한다.

## 6. Mom Test 질문

아래 질문은 기능 선호를 묻는 대신 과거의 구체 경험, 실제 행동, 돈·시간·리스크를 확인하도록 구성했다.

1. 최근에 고객 피드백이나 리뷰를 직접 분류해야 했던 일이 있었나요? 그때 어떤 자료를 받았고, 실제로는 어떤 순서로 정리했나요? 그 작업에 시간이 얼마나 걸렸고, 잘못 분류되면 어떤 문제가 생겼나요?

2. 가장 최근에 “긍정/부정/중립”처럼 의견을 판단해야 했던 사례를 떠올려 주세요. 판단 기준을 어디에 적어두었고, 실제로 누가 그 기준을 바꿨나요? 기준이 흔들렸을 때 재작업에 얼마나 시간을 썼나요?

3. 지난번에 텍스트를 정해진 형식으로 입력하거나 정리해야 했던 경험이 있나요? 실제로 사람들이 그 형식을 잘 지켰나요? 입력 실수 때문에 분석이 틀어졌을 때 누가 확인하고 고쳤나요?

4. 최근에 엑셀, CSV, 설문 응답, 고객 문의 같은 비정형 데이터를 수업이나 업무에서 다룬 적이 있나요? 데이터를 분석 가능한 형태로 만들기 위해 실제로 어떤 수작업을 했나요? 그 정리 작업이 전체 과제나 업무에서 차지한 비중은 어느 정도였나요?

5. 피드백 분류 결과를 다른 사람에게 설명하거나 보고해야 했던 가장 최근 사례가 있나요? “왜 이 문장이 이 카테고리인가”를 어떻게 설명했나요? 설명이 부족해서 신뢰를 잃거나 다시 검토한 적이 있었나요?

6. 리팩토링이나 코드 개선 학습 중에 조건 분기, 하드코딩된 규칙, 단순 출력 구조를 만난 적이 있나요? 실제로 어디부터 고쳤고, 무엇을 기준으로 개선 우선순위를 정했나요? 잘못 건드려서 동작이 깨진 경험이 있다면 비용이 얼마나 컸나요?

7. 최근에 팀원과 함께 분류 기준을 맞춰야 했던 일이 있었나요? 각자 다른 기준으로 판단한 결과를 어떻게 맞췄나요? 기준 불일치 때문에 회의, 재분류, 리뷰에 추가로 쓴 시간이 있었나요?

8. 고객 피드백 분석 결과를 파일, 화면, 발표 자료 등 다른 형태로 옮긴 경험이 있나요? 실제로 어떤 결과물이 필요했고, 원본 결과와 옮긴 결과가 달라진 적이 있었나요? 그 차이를 발견하지 못했을 때 어떤 리스크가 있었나요?

9. 학습자 입장에서 “이 코드를 왜 고쳐야 하는지”가 명확하지 않았던 리팩토링 과제를 해본 적이 있나요? 그때 어떤 단서가 있으면 문제를 더 잘 정의할 수 있었나요? 문제 정의가 모호해서 구현 시간을 낭비한 적이 있었나요?

10. 최근에 작은 규칙 변경이 여러 곳의 수정으로 번진 경험이 있나요? 실제로 몇 군데를 바꿨고, 빠뜨린 곳은 어떻게 발견했나요? 이런 변경이 반복되면 유지보수 시간이나 오류 위험이 얼마나 커졌나요?

## 7. 문제 정의

### 7.1. 표면 문제

고객 피드백 분석 시스템은 수동 입력과 CSV 업로드를 통해 피드백을 분석하지만, 입력 검증과 분석 기준, 필터 기준, 출력 결과가 명확히 연결되어 있지 않다.

또한 현재 구조는 여러 책임이 섞여 있어 작은 정책 변경도 여러 영역의 수정으로 번지고, 결과 일관성을 보장하기 어렵다.

### 7.2. 개선된 정의

이 시스템의 본질적인 문제는 피드백을 분석하는 기준이 시스템 전체에서 하나의 신뢰 가능한 규칙으로 관리되지 않는다는 점이다.

사용자는 피드백 입력 후 감정, 카테고리, 필터링, 다운로드 결과가 모두 같은 기준으로 산출되기를 기대하지만, 현재 구조는 그 기대를 안정적으로 보장하기 어렵다.

따라서 개선의 중심은 기능 추가가 아니라 입력, 분석, 필터, 출력이 동일한 정책과 동일한 데이터 흐름을 공유하도록 만드는 것이다.

수동 입력과 CSV 입력은 서로 다른 진입점일 뿐이며, 내부에서는 같은 검증 규칙과 분석 단위를 사용해야 한다.

감정, 카테고리, 출력 포맷은 변경 가능성이 높은 영역이므로 코드 내부에 고정하기보다 외부화된 정책과 등록 가능한 단위로 관리되어야 한다.

궁극적으로 이 프로젝트의 문제는 “피드백 분석 기능이 부족하다”가 아니라 “분석 결과를 신뢰하게 만드는 구조적 일관성이 부족하다”로 정의하는 것이 더 정확하다.

### 7.3. 핵심 Invariant

- 동일한 피드백 문장은 수동 입력과 CSV 입력에서 동일한 분석 결과를 가져야 한다.
- 분석 통계와 필터링 결과는 항상 같은 감정·카테고리 기준을 사용해야 한다.
- 모든 입력 데이터는 분석 전에 필수 텍스트 존재 여부와 빈 값 여부가 검증되어야 한다.
- 새로운 감정 또는 카테고리 단위는 기존 분석 흐름 변경 없이 등록 가능해야 한다.
- 화면 출력과 다운로드 출력은 동일한 분석 결과 원천에서 생성되어야 한다.

### 7.4. 훈련하려는 사고 능력

- 책임 분리 관점에서 코드 구조의 변경 이유를 식별하는 능력
- 입력, 처리, 출력 사이의 데이터 일관성을 추적하는 능력
- 확장 가능성이 높은 정책 영역을 코드가 아닌 규칙 단위로 바라보는 능력

## 8. 진짜 위험 가정

- 학습자와 사용자는 현재 구조의 문제가 기능 부족이 아니라 입력, 변환, 출력 기준의 불일치라는 점을 실제 고통으로 느끼고 있다.
- 단순 입력과 조건 분기 기반 변환 구조가 학습 목적에는 충분히 현실적인 문제 상황을 드러낸다.
- 사용자는 단순한 출력 결과라도 왜 그런 결과가 나왔는지 추적하고 설명할 필요를 강하게 느낀다.
