# 04. .cursorrules 다단계 보고서

## 1. 세션 목적

이번 세션의 목적은 `feedback_analyzer_A02` 프로젝트에서 Cursor AI가 따를 `.cursorrules` 규칙을 YAML 구조로 재정리하고, Java 21 기반의 코드 스타일, 아키텍처, TDD, 테스트, 금지 패턴, 파일 구조, AI 행동 규칙을 단계적으로 완성하는 것이다.

주요 수행 내용은 다음과 같다.

- `.cursorrules` YAML 최상위 구조 정의
- `UnitConverter` 기준 TDD 단계 규칙 작성
- 기존 `.cursorrules` 전체 검토
- Java 21 기준 전체 YAML 규칙 작성
- 실제 `.cursorrules` 파일 반영
- 반영 후 linter 진단 확인

## 2. 초기 YAML 뼈대 정의

첫 단계에서는 `.cursorrules`에 사용할 최상위 키만 정의했다.

정의한 최상위 섹션은 다음과 같다.

- `project`
- `code_style`
- `architecture`
- `tdd_rules`
- `testing`
- `forbidden`
- `file_structure`
- `ai_behavior`

각 섹션 앞에는 80자 폭의 `#` 구분선 주석을 두는 형식을 사용했다.

## 3. TDD 규칙 구성

두 번째 단계에서는 `tdd_rules` 블록을 `Java UnitConverter` 기준으로 구성했다.

TDD 단계는 다음 세 가지로 나눴다.

- `red_phase`
- `green_phase`
- `refactor_phase`

각 단계는 다음 하위 항목을 갖도록 설계했다.

- `description`
- `rules`
- `must_not`

이후 전체 YAML 작성 단계에서 각 단계의 의미를 구체화했다.

`red_phase`는 실패하는 테스트를 먼저 작성하여 `UnitConverter` 요구 동작을 고정하는 단계로 정의했다.

`green_phase`는 작성한 테스트를 통과하는 최소한의 구현을 만드는 단계로 정의했다.

`refactor_phase`는 테스트가 green인 상태에서 구현과 테스트의 중복을 정리하는 단계로 정의했다.

## 4. 기존 .cursorrules 검토

기존 `.cursorrules` 파일은 자연어 문서 형태로 작성되어 있었다.

검토 기준은 다음 네 가지였다.

- YAML 문법 오류
- 누락 섹션
- `tdd_rules`와 `forbidden` 충돌
- Cursor가 지키기 어려운 규칙

검토 결과는 다음과 같았다.

- 기존 파일은 YAML 문서 구조가 아니었다.
- 요청한 최상위 키 8개가 모두 누락되어 있었다.
- `tdd_rules`와 `forbidden` 섹션이 없어서 명시적 충돌은 확인할 수 없었다.
- 테스트 green 보장, 완전한 backward compatibility 보장, 레이어 책임 분리 준수 등은 Cursor가 항상 보장하기 어려운 규칙으로 분류했다.

## 5. 전체 YAML 규칙 작성

이후 Java 21 기준으로 `.cursorrules` 전체 YAML을 구성했다.

`project`에는 프로젝트 역할, 언어, 버전, 빌드 도구, 프레임워크, 템플릿 엔진, 테스트 프레임워크, 커버리지 도구, 포매터를 정의했다.

기존 `.cursorrules`에 있던 핵심 도메인 규칙은 `project.domain_rules`에 보존했다. 특히 피드백 데이터의 `text` 컬럼은 필수이며, 실제 피드백 내용을 담아야 하고, 명시적 스키마 변경 요청 없이는 이름과 의미를 바꾸지 않아야 한다는 규칙을 유지했다.

`code_style`에는 Google Java Format, Java 네이밍 규칙, `boundary`, `control`, `entity` 패키지 책임과 모듈 의존 관계를 정의했다.

`architecture`에는 BCE 관점의 계층 정의와 의존성 방향을 정리했다.

```text
boundary -> control
control -> entity
entity -> none
```

`testing`에는 JUnit 5 고정, AAA 구조, fixture 규칙, 커버리지 기준을 정의했다.

커버리지 기준은 다음과 같이 설정했다.

- line coverage: 80
- branch coverage: 70
- 핵심 도메인 로직, `UnitConverter` 변환 규칙, 예외 및 경계값 처리를 필수 대상으로 지정

`forbidden`에는 다음 금지 패턴을 `pattern`, `reason`, `alternative` 형식으로 정리했다.

- `System.out` 디버그 남발
- 매직 넘버 하드코딩
- 광범위 `catch(Exception)` 무시
- `public` 필드 남용
- God class

`file_structure`에는 `boundary`, `control`, `entity`, `tests` 관점의 트리 주석을 작성했다.

`ai_behavior`에는 레이어 위반 금지, 테스트 우선, green 이후 리팩터링, 동작 변경과 리팩터링 분리, 기존 컨벤션 우선, 불확실한 요구사항 확장 금지를 정의했다.

## 6. 파일 반영

최종 YAML은 프로젝트 루트의 `.cursorrules` 파일에 반영했다.

반영 시 기존 자연어 문서 형태의 규칙을 YAML 구조로 교체했다.

보존한 기존 규칙은 다음과 같다.

- Java, Maven, Spring Boot, Thymeleaf, JUnit 5, JaCoCo 프로젝트 맥락
- feedback data의 `text` 컬럼 필수 규칙
- 리팩터링은 테스트 green 이후 수행한다는 원칙
- 기존 프로젝트 컨벤션을 우선한다는 원칙
- generated build output인 `target/`을 임의로 수정하지 않는 방향
