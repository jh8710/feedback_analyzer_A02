# 01. 프로젝트 개요 & 준비 보고서

## 1. 세션 목적

이번 세션의 목적은 `feedback_analyzer_A02` 프로젝트의 전체 구조와 미션을 파악하고, 이후 Cursor AI가 일관되게 따라야 할 프로젝트 규칙을 준비하는 것이다.

주요 수행 내용은 다음과 같다.

- 프로젝트 루트에 Cursor AI용 `.cursorrules` 파일 작성
- `README.md`, `project_purpose.md`, `pom.xml` 기반 프로젝트 목적 분석
- `src/main/java`, `src/main/resources`, `src/test/java` 구조 확인
- 현재 코드의 책임 분배, 테스트 상태, 리팩토링 우선순위 정리

## 2. 프로젝트 개요

프로젝트명은 **리팩토링 챌린지: 고객 피드백 분석 시스템(Feedback Analyzer)** 이다.

이 애플리케이션은 자연어 기반 고객 피드백 데이터를 수집하고, 키워드 기반 분류와 감정 분석을 수행하며, 결과를 Thymeleaf 화면에서 확인할 수 있도록 구성된 Spring Boot 웹 애플리케이션이다.

핵심 기능은 다음과 같다.

- 텍스트 피드백 직접 입력
- CSV 파일 업로드
- 키워드 기반 카테고리 분류
- 긍정/중립/부정 감정 분석
- 감정 및 키워드 기반 필터링
- 분석 결과 화면 표시
- CSV 다운로드

## 3. 기술 스택

이번 세션에서 프로젝트 규칙으로 정의한 기술 스택은 다음과 같다.

- Java 21
- Maven
- Spring Boot
- Thymeleaf
- JUnit 5
- JaCoCo

다만 현재 `pom.xml` 기준 실제 설정에는 차이가 있다.

- Spring Boot 버전은 `3.5.3`
- 현재 `java.version`은 `17`
- JaCoCo 플러그인은 아직 설정되어 있지 않음
- OpenCSV 의존성이 포함되어 있음

따라서 이후 준비 단계에서 Java 21 반영 여부와 JaCoCo 설정 추가 여부를 확인할 필요가 있다.

## 5. 주요 컴포넌트 역할

### 5.1. `FeedbackController`

웹 요청 처리를 담당한다. 현재는 화면 진입, 텍스트 입력, CSV 업로드, 분석 호출, 필터링, 다운로드까지 대부분의 흐름을 직접 처리한다.

현재 책임이 가장 많이 집중된 클래스이며, 서비스 계층 분리의 우선 후보이다.

### 5.2. `TextAnalyzer`

피드백 텍스트의 감정 분석과 키워드 카운팅을 담당한다.

현재 `sent`, `kw` 같은 축약형 메서드명을 사용하고 있으며, 분석 결과를 static 필드에 저장하는 전역 상태 냄새가 있다.

### 5.3. `Filters`

감정 및 카테고리 기준 필터링을 담당한다.

감정 키워드를 `Constants`와 별도로 다시 가지고 있어 분석 결과와 필터 결과가 서로 달라질 위험이 있다.

### 5.4. `Constants`

감정 키워드와 카테고리 키워드를 하드코딩 형태로 관리한다.

중복 키워드와 복잡한 `Map<String, Object>` 구조가 있어 타입 안정성과 유지보수성 개선 여지가 있다.

### 5.5. `Session`

현재 피드백 목록을 static 전역 상태로 관리한다.

웹 애플리케이션 관점에서는 사용자 간 데이터가 섞일 수 있고, 동시성 문제도 발생할 수 있어 중요한 개선 대상이다.

### 5.6. `Feedback`

피드백 데이터 모델이다.

`text`, `sentiment`, `category` 필드를 가지고 있지만 현재 getter는 `text`만 제공한다. 분석 결과를 모델에 담을지, 별도 DTO로 분리할지 결정이 필요하다.

### 5.7. `index.html`

Thymeleaf 기반 단일 화면이다.

입력, 업로드, 필터, 분석 결과 표시가 모두 한 파일에 들어 있어 화면 규모가 커질 경우 fragment 분리나 뷰 모델 정리가 필요하다.

## 6. 절대 도메인 규칙

이번 세션에서 `.cursorrules`에 반영한 핵심 도메인 규칙은 다음과 같다.

- 피드백 데이터에는 반드시 `text` 컬럼이 있어야 한다.
- `text` 컬럼에는 실제 피드백 내용이 포함되어야 한다.
- 명시적 스키마 변경 요청 없이 `text` 컬럼을 이름 변경, 삭제, 재해석하지 않는다.
- CSV를 읽거나 쓸 때 `text` 컬럼 존재 여부를 검증해야 한다.

현재 CSV 업로드 구현은 헤더를 건너뛰고 첫 번째 컬럼을 바로 사용한다. 따라서 `text` 헤더 검증과 컬럼 위치 확인이 향후 필수 개선사항이다.

## 7. 테스트 현황

현재 테스트는 `DemoApplicationTests`의 `contextLoads()` 하나뿐이다.

테스트 프레임워크는 JUnit 5와 `@SpringBootTest` 기반으로 구성되어 있으나, 실제 비즈니스 로직 테스트는 부족하다.

우선 보강이 필요한 테스트는 다음과 같다.

- `TextAnalyzer` 감정 분석 테스트
- `TextAnalyzer` 키워드 분류 테스트
- `Filters` 감정/카테고리 필터 테스트
- CSV 업로드 시 `text` 컬럼 필수 검증 테스트
- 다운로드 CSV 헤더가 `text`인지 확인하는 테스트

리팩토링은 테스트가 Green 상태일 때만 진행하는 규칙을 적용해야 한다.

## 8. 리팩토링 우선순위

1. 현재 동작을 보호하는 테스트 추가
2. CSV `text` 컬럼 검증 로직 보강
3. `FeedbackController`에서 분석, 파일 처리, 필터링 책임 분리
4. `Constants`와 `Filters`의 감정 키워드 중복 제거
5. `Session` static 전역 상태 제거 또는 명확한 세션 관리 방식 도입
6. 매직 넘버와 하드코딩 문자열을 의미 있는 상수로 정리
7. JaCoCo 설정 추가 및 커버리지 기준 수립
